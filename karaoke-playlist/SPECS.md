- 2026-08-15 : correction d'un bug où le bouton "Passer" pouvait vider toute la file d'attente. Cause : `player.html` retirait la tête de file sans condition (`dequeueCurrent`) quand une vidéo se terminait ; si l'écran de contrôle avait déjà retiré cette même chanson via "Passer" juste avant, un ENDED tardif du lecteur (course connue avec `loadVideoById` côté API YouTube) retirait une deuxième chanson, pouvant vider une file de 2 titres. Remplacé par `KaraokeState.removeIfCurrent(id)` : la tête de file n'est retirée que si son `id` correspond encore à la chanson que le lecteur vient de terminer, rendant l'opération idempotente entre les deux écrans.
- 2026-08-15 : correction d'un bug d'affichage dans `karaoke-playlist/index.html` — l'API YouTube Data v3 renvoie `snippet.title`/`snippet.channelTitle` HTML-échappés (ex: "Pour que tu m&#39;aimes encore"), et comme le rendu utilise `textContent` (volontairement, pas d'innerHTML), ces entités s'affichaient telles quelles au lieu d'être décodées. Ajout de `decodeHtmlEntities()` (décodage sûr via un `<textarea>` temporaire, jamais interprété comme balises) appliqué aux titres/chaînes dès la lecture des résultats de recherche, avant affichage ET avant stockage dans la file (`KaraokeState.addTrack`).
- 2026-08-15 : certaines vidéos (ex: chaîne Sing King) ont l'intégration désactivée par leur propriétaire — injouables dans `player.html`. `karaoke-playlist/index.html` appelle maintenant `videos.list?part=status` après chaque recherche pour exclure des résultats les vidéos avec `embeddable:false`, avant même qu'elles puissent être ajoutées à la file.
- 2026-08-15 : le filet de sécurité `armStallTimer`/`STALL_TIMEOUT_MS` ajouté juste avant dans `player.html` (skip auto si la lecture ne démarre pas en 15s) sautait en fait TOUTES les chansons — le timer n'était jamais annulé au passage en `PLAYING`, donc il se déclenchait systématiquement 15s après le début de n'importe quelle vidéo, y compris celles qui jouaient normalement. Supprimé entièrement à la demande de l'utilisateur plutôt que réparé : le filtrage `embeddable` à la recherche couvre déjà la cause réelle, et `onError` reste le filet de sécurité pour le reste.
- 2026-08-15 : le stall timer a été restauré à la demande, cette fois avec `onPlayerStateChange` qui appelle `clearStallTimer()` sur l'état `PLAYING` (pas seulement `ENDED`) — vérifié par simulation qu'une vidéo qui démarre normalement n'est plus jamais sautée, et qu'une vidéo bloquée l'est toujours après 15s.
- 2026-08-15 : correction d'un `ReferenceError: KaraokeState is not defined` — `<script src="state.js">` et `window.open('player.html', ...)` étaient en chemins relatifs. Si la page est ouverte sans slash final (`/karaoke-playlist` au lieu de `/karaoke-playlist/`, ce que fait le serveur local `serve` de `npm run start:local` sans redirection, contrairement à `python -m http.server` qui redirige en 301), le navigateur résout ces chemins relatifs contre la racine du site au lieu du dossier `karaoke-playlist/`. Remplacés par des chemins absolus (`/karaoke-playlist/state.js`, `/karaoke-playlist/player.html`) dans `index.html` et `player.html`, insensibles à la présence du slash final.

- 2026-08-18 : ajout d'un flux invités (QR code) à `karaoke-playlist/` synchronisé via Firestore, pour laisser les gens ajouter des chansons depuis leur téléphone pendant la soirée. Contrainte de conception : le serveur dj-mix n'est joignable que depuis le LAN de l'hôte (ex. `https://192.168.8.149:8443`), donc une Cloud Function (infra Google Cloud) ne peut PAS l'appeler directement — seul l'écran de contrôle (sur le LAN, déjà configuré avec le token API) le peut. Architecture retenue :
  - `player.html` affiche en permanence un QR code (lib `qrcodejs` via CDN, panneau discret en bas à droite) encodant `guest.html?session=<id>` — `id` vient de `state.js#getSessionId()` (UUID généré une fois, partagé avec l'écran de contrôle via le même localStorage).
  - `guest.html` (nouvelle page mobile) : un invité tape juste "Titre - Artiste" en texte libre, sans recherche/prévisualisation (impossible sans accès direct à dj-mix) ; le formulaire appelle la Cloud Function callable `submitSongRequest` (jamais d'écriture Firestore directe depuis le navigateur invité) et suit ensuite le statut de sa demande en temps réel (`pending` → `done`/`failed`).
  - `functions/index.js` (Cloud Function `submitSongRequest`, 2ᵉ génération, SDK Admin) : valide `sessionId`/`query`, plafonne à 30 demandes `pending` par session (garde-fou anti-abus, pas d'App Check), puis crée `sessions/{sessionId}/requests/{id}` avec `status:'pending'`.
  - `index.html` (écran de contrôle) : `<script type="module">` séparé qui écoute `sessions/{sessionId}/requests` en temps réel (`watchPendingRequests`), appelle `POST /api/video/download` avec `{trackName: query, searchQuery: query}` pour chaque demande en attente (dédupliquée via un `Set` local le temps du téléchargement, potentiellement long), ajoute le résultat à la file locale comme un ajout manuel, puis marque la demande traitée (`markRequestDone` = suppression du doc) ou échouée (`markRequestFailed` = `status:'failed'` + message).
  - `firestore.rules` : `create` interdit aux clients (uniquement la Cloud Function, SDK Admin) sur `sessions/*/requests/*` ; `read`/`update`/`delete` ouverts (le `sessionId`, UUID aléatoire non déductible, sert de capacité d'accès — modèle volontairement simple pour une appli de soirée entre invités de confiance).
  - `firebase-config.js` contient des valeurs placeholder (`REMPLACE_MOI`) à remplacer par la config du projet Firebase réel de l'utilisateur avant que quoi que ce soit ne fonctionne.
  - Vérifié : QR code décodé pixel-par-pixel via jsQR (URL exacte confirmée), toutes les pages chargent sans erreur JS avec la config Firebase placeholder. Le flux Firestore de bout en bout (invité → Cloud Function → écran de contrôle → dj-mix) n'a pas pu être testé faute de vrai projet Firebase configuré.
