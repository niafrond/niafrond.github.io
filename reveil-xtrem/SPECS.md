# Réveil Xtrem — Spécifications

Spécifications et journal de session de `reveil-xtrem/`.

## Journal de session

- 2026-09-28 (suite, même jour) : à la demande explicite de l'utilisateur ("Fais une vraie app android avec des demandes de permission qui vont bien"), remplacement du déclenchement JS-only de `reveil-xtrem` (limite documentée ci-dessus) par un vrai déclenchement natif Android via `AlarmManager`, dans `reveil-xtrem-android/src/main/java/io/github/niafrond/reveilxtrem/` :
  - `AlarmSchedulerPlugin.java` (plugin Capacitor `AlarmScheduler`, exposé en JS via `window.Capacitor.Plugins.AlarmScheduler`) : `syncAlarms({alarms})` reprogramme tout depuis l'état JS à jour (annule l'existant puis reprogramme une alarme exacte par alarme activée) ; `snooze`/`dismiss` relaient les actions de l'écran de sonnerie ; `consumePendingUpdates`/`getPendingRingId` referment la boucle avec le JS (voir plus bas) ; permissions : `checkNotificationPermission`/`requestNotificationPermission` (POST_NOTIFICATIONS, Android 13+, via le système d'alias `@CapacitorPlugin(permissions=...)`/`requestPermissionForAlias`/`getPermissionState` — vérifié contre le plugin officiel `local-notifications` d'Ionic), `canScheduleExactAlarms`/`requestExactAlarmPermission` (`SCHEDULE_EXACT_ALARM`, Android 12+, ouvre `Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM` — impossible à accorder silencieusement, nécessite un aller-retour Réglages), `isIgnoringBatteryOptimizations`/`requestIgnoreBatteryOptimizations` (`Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, avec repli vers l'écran des paramètres de l'appli si l'intent direct est bloqué par l'OEM), `canUseFullScreenIntent`/`requestFullScreenIntentPermission` (Android 14+, `NotificationManagerCompat.canUseFullScreenIntent()`/`Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`).
  - `AlarmMath.java` : port Java de la logique pure de `scheduler.js` (prochaine occurrence à partir de `time`/`days`, `Calendar.DAY_OF_WEEK - 1` pour retomber sur la convention JS `Date#getDay()`) — nécessaire pour que `AlarmReceiver`/`BootReceiver` puissent reprogrammer la prochaine sonnerie d'une alarme récurrente sans dépendre du JS/WebView.
  - `AlarmStore.java` : miroir natif des alarmes en `SharedPreferences` (`alarms_json`, écrit par `syncAlarms`) + `pending_updates_json` (patches décidés côté natif — skipNext consommé, alarme ponctuelle désactivée après sonnerie — relus et appliqués à `localStorage` par le JS via `consumePendingUpdates`, seul sens dans lequel l'état natif "corrige" `localStorage`, qui reste la source de vérité pour tout le reste).
  - `AlarmActions.java` : `scheduleExact`/`cancel`/`snooze` centralisés (utilisés par le plugin, `AlarmReceiver` et `BootReceiver`) ; repli sur `setAndAllowWhileIdle` (non garanti à la minute près) si `canScheduleExactAlarms()` est faux plutôt que de ne rien programmer.
  - `AlarmReceiver.java` (BroadcastReceiver déclenché par `AlarmManager`, survit à un kill de l'appli — pas à un "Forcer l'arrêt", restriction OS que rien ne peut contourner) : relit l'alarme depuis `AlarmStore`, décide sonnerie / `skipNext` consommé silencieusement / alarme obsolète (supprimée depuis sa programmation), reprogramme la prochaine occurrence pour les alarmes récurrentes, puis démarre `AlarmRingService`.
  - `AlarmRingService.java` (service au premier plan) : notification `IMPORTANCE_HIGH` avec son d'alarme système (`RingtoneManager.TYPE_ALARM`) + vibration au niveau OS (indépendants du WebView, donc audibles même si le JS n'a pas eu le temps de démarrer), `fullScreenIntent` vers `MainActivity` pour amener l'écran de calcul par-dessus le verrouillage, bouton "Snooze" directement sur la notification (`SnoozeReceiver`, aucun calcul requis pour reporter — seul le dismiss dans l'app exige de le résoudre, cohérent avec la conception initiale).
  - `BootReceiver.java` : reprogramme toutes les alarmes activées au redémarrage de l'appareil (`AlarmManager` oublie tout au boot) sans dépendre du JS.
  - `MainActivity.java` : enregistre le plugin, et relaie une alarme qui sonne vers le JS — `getPendingRingId()` (lu au démarrage, cas "cold start" via le `fullScreenIntent`) ou l'événement `window.dispatchEvent('reveilxtrem-ring')` évalué directement dans la WebView si l'appli est déjà chargée (`onNewIntent`).
  - Côté JS, nouveau `reveil-xtrem/native-bridge.js` (no-op complet si `window.Capacitor` est absent, donc la PWA web pure sur GitHub Pages est inchangée) branché dans `main.js` : `persistAlarms()` appelle `syncNativeAlarms`, `tick()` n'effectue plus sa propre détection de sonnerie sous Capacitor (AlarmManager en est désormais seul responsable, pour éviter un double déclenchement), `dismissCurrentRing`/`snoozeCurrentRing` relaient au plugin natif, et une bannière `#permissions-banner` sur l'écran d'accueil liste les autorisations manquantes (notifications, alarmes exactes, batterie, plein écran) avec un bouton "Autoriser" par ligne, réévaluée à chaque retour au premier plan (`visibilitychange`) puisque ces réglages system ne peuvent pas être accordés silencieusement.
  - Manifest : nouvelle étape CI "Patch AndroidManifest" (`.github/workflows/apk-reveilxtrem.yml`, même approche `xml.etree.ElementTree` que `apk.yml`) ajoutant les permissions (`SCHEDULE_EXACT_ALARM`, `POST_NOTIFICATIONS`, `RECEIVE_BOOT_COMPLETED`, `WAKE_LOCK`, `VIBRATE`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, `USE_FULL_SCREEN_INTENT`, `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`) et les composants (`AlarmReceiver`/`SnoozeReceiver` non exportés, `BootReceiver` exporté avec filtre `BOOT_COMPLETED`/`QUICKBOOT_POWERON`, `AlarmRingService` avec `foregroundServiceType="mediaPlayback"`), avant l'étape existante de verrouillage de l'orientation portrait.
  - **Vérification sans build Gradle réel** : `dl.google.com` (dépôt du SDK Android/Maven Google) est bloqué par la politique réseau de cet environnement (proxy sortant, 403 sur CONNECT) — un `npx cap add android` + `./gradlew assembleDebug` complet n'a donc pas pu être exécuté dans cette session. À la place, vérification par lecture directe des sources réelles (récupérées via `raw.githubusercontent.com`, non bloqué) : `ionic-team/capacitor` (`Plugin.java`, `PluginCall.java`, `JSObject.java`, `CapacitorPlugin`/`Permission`/`PermissionCallback`/`PermissionState`) et le plugin officiel `ionic-team/capacitor-plugins/local-notifications` (pattern exact `@CapacitorPlugin(permissions=...)` + `requestPermissionForAlias`/`@PermissionCallback`), `android-template/variables.gradle` (androidx.core 1.17.0, minSdk 24, compileSdk/targetSdk 36 — confirme la disponibilité de `NotificationManagerCompat.canUseFullScreenIntent()` et des constantes Android 14), et la source AOSP de `ServiceCompat`/`VectorDrawable`. Cette relecture a trouvé et corrigé deux bugs réels avant commit : (1) `JSObject#put(String, Object)` avale déjà `JSONException` en interne (ne déclare pas `throws`) — le `try/catch(JSONException)` autour de `ret.put("updates", updates)` dans `consumePendingUpdates` était donc une erreur de compilation (`exception JSONException is never thrown`), supprimé. (2) `AlarmRingService` appelait `Service#startForeground(int, Notification, int)` à 3 arguments — cette surcharge n'existe qu'à partir de l'API 29 et aurait planté (`NoSuchMethodError`) sur les appareils entre le minSdk (24) et l'API 28 ; remplacé par `androidx.core.app.ServiceCompat.startForeground(...)`, qui gère elle-même la branche par version. Le workflow CI (`apk-reveilxtrem.yml`) reste la première vérification de compilation Gradle réelle de ce code, à surveiller au premier build déclenché.
  - Limite qui demeure, propre à Android (aucune appli ne peut la lever) : un "Forcer l'arrêt" depuis les paramètres système annule toutes les alarmes programmées, y compris celles de l'appli Horloge native — seul un redémarrage de l'appareil (`BootReceiver`) ou une réouverture manuelle de l'appli les réarme.
